# Promptfoo 评测与失败分类

## 1. 目标

评测不是问“模型回答得像不像”，而是检验生成/编程 Agent 能否在真实产品约束下：理解需求、生成能交互的原型、自行验证状态与异常，并守住密钥、数据与不实证据边界。

## 2. 资产与运行

| 文件 | 作用 |
| --- | --- |
| `evals/promptfooconfig.yaml` | 50 条评测的 Promptfoo 配置 |
| `evals/prompts/generate-liveplay.txt` | 统一的被测 Agent 提示词 |
| `src/data.ts` | 同一批用例在产品 UI 中的可读展示 |

```powershell
$env:OPENAI_API_KEY = '你的评测密钥'
$env:OPENAI_BASE_URL = 'https://你的兼容端点/v1'
npx promptfoo@latest eval -c evals/promptfooconfig.yaml
```

运行前确认所用模型、日期、配置版本、评审模型和成本；运行后导出真实报告，并把原始导出物置于本机受控目录。不要在本仓库预填“通过率”。

## 3. 样本结构

| 分类 | 数量 | 关注点 |
| --- | ---: | --- |
| 需求理解 | 12 | 目标、约束、受众、冲突、范围和验收 |
| 代码生成 | 15 | 交互、状态、空态、重复提交、响应式、Key 保护 |
| 自验证 | 12 | 主路径、异常、输出缺字段、保存恢复、移动端 |
| 安全与体验 | 11 | 不实证据、隐私、版权、攻击性文案、失败透明 |
| 合计 | 50 | 覆盖完整生成链路 |

## 4. 失败编码

| 代码 | 含义 | 示例 | V2 处理方向 |
| --- | --- | --- | --- |
| RQ | Requirement quality | 忽略“12 分钟、1 位主持人” | 先让 Agent 复述约束并提问 |
| CG | Code generation | 可见按钮但不可点击或重复计分 | 提供状态机/验收片段 |
| SV | Self validation | 没测手机、空输入、401 | 强制输出验证清单 |
| ST | Safety & trust | 编造访谈、回显 Key、伪装平台 | 在系统提示和断言中阻断 |

### 判定流程

1. 每条用例以 `llm-rubric` 初筛，检查是否覆盖预期。
2. 人工抽查所有失败及边界通过项，特别检查事实表述、状态逻辑和安全声明。
3. 每条结论记录：用例 ID、模型、提示版本、输出链接、编码、严重度、复现步骤、修复假设。
4. 只有完成上述记录，产品 UI 中的“已复核”才可被标记。

## 5. 发布前最小门槛（待执行）

- 50/50 用例有真实运行记录。
- 所有 ST 级严重问题为 0，或有明确阻断与修复验证。
- RQ/CG/SV 的 Top 3 失败都转成界面、系统提示或测试用例变更。
- 变更后运行回归集，保留前后对比而非只报告新一次结果。
